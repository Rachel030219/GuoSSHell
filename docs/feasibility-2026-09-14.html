〇、结论先行

可以做，而且比预想的干净得多。 你关心的那件事——alacritty 后端能不能在 iOS 上跑——答案是分层的，我把它拆成四层，其中前两层我在本机用真实编译和链接验证过，不是推测：

层问题判定
编译层alacritty_terminal 0.26.0 及其全链依赖（rustix-openpty、signal-hook、polling、vte、libc）能不能为 aarch64-apple-ios 编译可以（已实测通过，零改动）
链接层它引用的 openpty / fork 符号在 iOS 上能不能解析可以（已实测生成并链接出 iOS dylib，符号从 libSystem 解析）
VT 语义层终端状态机、ANSI/UTF-8 解析、grid、选择、搜索能不能在 iOS 上正确工作可以，而且这部分根本不碰 OS
PTY / 进程层iOS 上能不能开一个本地 shell（alacritty tty::new 那条路）不行，且不可能

关键澄清，也是本次调研最容易被误读的一点：「alacritty 后端能否在 iOS 上跑」这个问题的正确答案，取决于你用它的哪一半。

  • rsHell 用 alacritty 只用了 纯解析器那一半：Term、grid、term::Config、vte::ansi::Processor、index、selection、vi_mode（我在源码里逐个 grep 确认过，见 §1）。
  • 它完全没有用 alacritty_terminal::tty / event_loop / thread / sync。本地 PTY 走的是 portable-pty-psmux 0.9.6。
  • 而 alacritty 的 tty 模块是 #[cfg(not(windows))] mod unix;——iOS 属于 unix，所以它会被编译进去，只是永远不会被调用。我实测确认它编得过、也链得过，所以你不会因为"无辜的死代码"被卡住。iOS 上真正做不到的是它背后的系统能力，不是这段 Rust 代码。
因此产品结论是： iOS / iPadOS 上只做远程 SSH 终端（PTY 在服务器侧，russh 开 session channel + pty-req + window-change，完全不需要本地 PTY）。桌面那套「本地 shell / 系统 OpenSSH」在 iOS 上砍掉或另立产品范围，不要试图移植。这条路线的可行性是"高"，不是"有条件"。

剩下的真实风险集中在三处，都不是 Rust 侧：① Flutter 端终端绘制的性能与字体度量；② iOS 输入（软键盘没有 Ctrl/Esc、IME 与按键分两路、Cmd 被系统占用）；③ 生命周期与内存（后台挂起必然断连；桌面的 100 MiB×5 滚动缓冲契约在手机上会触发 jetsam）。这三项都有明确解法，但都必须用真机 Gate 验，不能靠推断。

另外一个前置修正：Rinf 在 v8 里已经不用 protobuf 了，它改成 serde + bincode、消息在 Rust 侧用 derive 定义、Dart 类由 rinf gen 生成。你要的"统一高效的对象规约"仍然能拿到，但拿到它的方式和你以为的不一样，而且它反过来更适合"Rust 是唯一真相源"这个约束。详见 §4。

一、我在本机跑出来的实测证据

下面每一条都是本次会话里在本机真实执行的命令与其输出，不是引文。你朋友的报告在 alacritty on iOS 这一节只给到"建议先尝试直接构建所需终端路径"，这次我把它变成了结论。

1.1 alacritty_terminal 0.26.0 全链为 iOS 编译 + 链接

建一个最小探针 crate，除 alacritty 外不含任何东西，然后为 iOS 目标做完整 build（不是 check）并产出静态库与动态库：

1.2 iOS SDK 层面的交叉验证

本机 Xcode 16.2 / iPhoneOS 18.2 SDK 的直接检视结果：

检查项结果含义
iPhoneOS18.2.sdk/usr/include/util.h 是否存在存在iOS 上确实有 util.h，且其中声明了 login_tty / openpty / forkpty，没有 __API_UNAVAILABLE(ios) 标注
usr/lib/libSystem.tbd 是否导出 _openpty / _forkpty / _login_tty / _posix_openpt / _fork全部导出所以"生成 PTY 设备对"这件事本身在 iOS 上是被允许的
usr/include/unistd.h 是否声明 fork没有声明这是最硬的信号：Apple 在头文件层面就不给你 fork
spawn.h 中 posix_spawn 的可用性__API_AVAILABLE(macos(10.5), ios(2.0))API 存在，但沙箱策略不允许 spawn 任意可执行文件（App Review 2.5.2）
这张表解释了一个很常见的误判。 "iOS 没有 openpty 符号"是错的（有），"所以 iOS 能做本地终端"也是错的（能建 PTY 对，但没法往 PTY 的另一端挂一个 shell 进程）。iOS 终端应用的现实做法是绕开 fork/exec：iSH 用 x86 用户态模拟 + 系统调用翻译，a-Shell / ios_system 把每个命令编成静态库、在同一个进程内直接调 main()。这已经不是"移植 rsHell 的本地 shell"，而是另一个产品。

1.3 整个 rsHell Rust 后端在 iOS 上只卡了一个地方

把仓库 clone 到临时目录，直接对 iOS 目标编译真正的 crate：

$ cargo check -p rshell-session --target aarch64-apple-ios  （修复前）
error: The `protected` feature is required on iOS
  --> apple-native-keyring-store-1.0.1/src/lib.rs:50:1
50 | compile_error!("The `protected` feature is required on iOS");
error: could not compile `apple-native-keyring-store` (lib) due to 1 previous error

根因很清楚：rshell-storage 里写的是

keyring = { version = "=4.1.5", default-features = false, features = ["v1"] }

而 keyring 4.1.5 的 v1 feature 展开为 apple-native-keyring-store/keychain、windows-native-keyring-store、zbus-secret-service-keyring-store。问题是 iOS 上根本没有 "legacy keychain" 这个 store——它只有 "protected data" store（这在 apple-native-keyring-store 的文档里写得很明确），所以那个 crate 在 iOS 上直接 compile_error!。这是一个纯粹的上游 feature 缺口，不是架构问题。

在临时克隆里补上 feature 统一（这行是探针用的临时改动，不是最终方案）之后：

1.4 rsHell 到底用了 alacritty 的哪些部分

在 crates/ 里搜 alacritty_terminal::(tty|event_loop|thread|sync)：零命中。实际用到的只有：

use alacritty_terminal::{Term, grid::Dimensions, index::Line, term::Config, vte::ansi::Processor};

对照 alacritty_terminal/src/lib.rs：

pub mod event;   pub mod event_loop;   pub mod grid;    pub mod index;
pub mod selection; pub mod sync;       pub mod term;    pub mod thread;
pub mod tty;     pub mod vi_mode;      pub use crate::term::Term; pub use vte;

结论：rsHell 需要的是 lib.rs 里的 6 个模块（event/grid/index/selection/term/vi_mode）+ vte，而对 OS 有强耦合的 4 个模块（event_loop/thread/tty/sync）它一个都不用。后者之所以还要能编译，只是因为 Cargo 没有给你 feature 开关。这一点决定了两件事：

  1. 不用 fork alacritty。既然实测编得过、链得过，就没有必要裁剪或维护补丁——朋友报告里"必要时裁剪未使用的宿主 PTY/event-loop 路径"这一步可以降级为可选的体积优化，不是阻塞项。
  2. 顺手应该做的是抽 crate，不是打补丁。把终端引擎抽成 rshell-terminal，只依赖 alacritty_terminal + 一个不重的渲染模型，让 iOS 链路不必牵扯 rshell-session 底下的 portable-pty / system-ssh / local-runtime。这与朋友报告"推荐先抽出 rshell-terminal"的判断一致，但理由从"避免依赖污染"升级为"避免把本地进程语义带进移动端"。

1.5 代码规模（决定工程量）

层Rust 行数iOS 处置
rshell-core（领域模型 + RenderFrame）≈ 4,240原样复用（已实测编过）
rshell-session（引擎适配、actor、SSH、PTY）≈ 7,036复用主体；transport::{local, pty, system_ssh, local_runtime*} 需 cfg 排除
rshell-storage（SQLite + 凭据 journal + 导入）—复用；凭据后端换 protected store

换句话说：要重写的是那 2.3 万行 GTK 层，要保留的是 1.1 万余行 Rust 内核。这个比例对"用 Flutter 写前端"这个诉求来说是健康的。

二、alacritty 后端在 iOS 上的四层判定（展开）

2.1 语义层为什么天然安全

Term<T> 的全部职责是把字节流变成 Grid 里的 cell 状态。它不知道窗口、不碰字体、不做 I/O——EventListener 是个纯回调，rsHell 自己实现的 EventSink 就是接这个口的。这部分搬上 iOS 与搬上 WebAssembly 的难度是同级的（只有 std）。rsHell 的 alacritty_adapter.rs 里构造终端就一句：

Term::new(Config { scrolling_history, kitty_keyboard, .. }, &GridSize::from(size), events)

没有线程、没有 fd、没有信号。这是整份报告里最让人安心的一个事实。

2.2 死代码层的代价与取舍

tty/unix.rs 会被编进 iOS 产物。它的 new() 做的是：openpty() → 取 uid/home（ShellUser::from_env）→ Command::new(shell).spawn()，并在 pre_exec 里 setsid() / chdir() / TIOCSCTTY / 重置 SIGCHLD 等六个信号 / 关闭 fd，然后用 signal_hook 注册 SIGCHLD。

在 iOS 上：编译无警告、链接成功、调用必失败（spawn 会因为无 fork 而被沙箱拒绝）。三个可选处置：

  • A（推荐，零成本）：什么都不做，只在 iOS 上把调用点用 #[cfg(not(target_os = "ios"))] 摘掉。rshell-session 那边本来也不走 alacritty 的 tty，天然满足。
  • B（省体积）：给 alacritty 提一个 pty feature 的上游 PR，或在 [patch.crates-io] 里放一个只改 lib.rs 一行的 fork（#[cfg(all(not(windows), feature = "pty"))] pub mod tty;）。这是唯一需要动 alacritty 的场景，且只有一行。
  • C（反模式）：为了让 tty 编不过而在 iOS 上伪造 openpty/fork 的 shim。不要做——那会把"本地 shell 不可用"这个真实约束伪装成"可用"。

2.3 为什么"本地 shell"必须在产品层面被显式砍掉

三条独立证据指向同一结论，缺一不可：

  • 头文件层：iOS SDK 的 unistd.h 不声明 fork（§1.2 实测）。
  • 运行时层：App Sandbox 不允许执行 bundle 之外的代码，posix_spawn 能叫但没东西可叫；iOS 上没有 /bin/sh 可依赖。
  • 审核层：App Review 2.5.2 要求应用自包含、不得下载/安装/执行引入新功能的代码。iOS 现存的 iSH / a-Shell 正是绕这条路走的（模拟器 / 同进程函数调用），而且 2020 年它们都曾被通知下架后又被恢复——这个类别是"处于 Apple 的宽容之下"，不是"受规则保护"。
对 rsHell 的直接后果： 桌面版的「本地 shell」是一个独立产品决策，不是移植工作。如果确实需要 iOS 本地计算，正确姿势是单独立项（a-Shell 式：自带 libios_system/WASM 工具集，同进程调用，无 fork），且要接受"命令集是编译期固定的、没有多进程、没有信号、没有 socket"这一整套限制。不要把它塞进本次迁移。

三、先划边界：什么必须留在 Rust

你这句话（"业务仍然尽可能使用 Rust 跑，能不改就不改，只有涉及渲染、交互等必不可少的部分才使用 Flutter 重写"）的可执行版本是下面这张表。它的价值在于：把"渲染/交互"这个模糊词收敛成可验收的职责清单，任何不在表里的东西落在 Dart 侧都算架构违规。

唯一真相源在 Rust（Dart 不得复制）唯一边界在 Flutter（Rust 不得依赖）
  • SSH 连接、认证、host key 校验、known_hosts
  • VT 状态机、grid、备用屏幕、scrollback、terminal modes
  • 键盘/鼠标的协议编码（CSI u、kitty keyboard、application cursor、mouse reporting）
  • 搜索、选择的语义（行列范围 → 文本）
  • 会话生命周期、重连、取消、错误分类
  • 连接目录、分组、tags、导入、SQLite 事务与凭据 journal
  • 渲染帧的生成（哪些行脏了、光标在哪、当前 modes）
  • 字形测量 → 行列数（唯一例外，见下）
  • 绘制（Impeller/Metal）、滚动动画、光标闪烁
  • 命中测试（像素 → cell 坐标）、选择手柄、手势
  • IME / 软键盘 / 辅助键条 / 硬件键盘事件采集
  • 系统服务：Keychain、UIPasteboard、文件导入、生命周期回调
唯一需要小心的一处"权威移交"：度量。 终端网格的行列数 N×M 由"可用像素空间 ÷ 单元格尺寸"决定，而单元格尺寸只能由 Flutter 侧的字体测量给出（Rust 侧没有字体栈）。所以正确姿势是：Flutter 是度量的权威，Rust 是状态的权威——Flutter 测出 cell 尺寸 → 算出 cols/rows → 通过一个 Resize 信号回传 → Rust 改 grid。这条路径必须是单向、幂等、可去重的，并且 DPR 只乘一次。桌面版 DESIGN 里"同一份测量驱动绘制、光标、选择、命中测试、IME、行列数"这个原则在 Flutter 上要重新实现一遍，但原则本身是对的，别丢。

反模式，明确禁止（这正是你不想看到的那条路）：Rust 输出原始字节 → Dart 侧 UTF-8 解码 → Dart 维护 terminal 状态机。它的直接后果是终端状态出现两份权威，滚动缓冲、选择、搜索、模式位会在两端漂移，而"靠同步字符串保持一致"是没有出路的。你朋友那份报告里把 xterm.dart 列为"主要备选"，走的就是这条路；本报告不采用。

四、桥：为什么用 Rinf，以及一个必须纠正的前提

4.1 先说好消息：Rinf 的官方立场和你的约束是同一句话

Rinf 的 README 原文："Rinf expects the entire business logic to be written in Rust, with Flutter only serving as the UI layer." 我在你机器上确认到 ~/.cargo/bin/rinf 已经装好了（另有 cargo-ndk），当前版本线是 8.10.1。它对 iOS 的支持在 README 里是 ✅ Tested，构建产物是 rinf.framework，由 Cargokit 接管。

比"哲学一致"更重要的是接口形状带来的约束力：Rinf 是单向信号（stream）模型，不是 RPC。它没有"从 Dart 调一个 Rust 函数并拿到返回值"这种表达能力——你必须定义 DartSignal（Dart→Rust）和 RustSignal（Rust→Dart）两个方向的独立消息。这对你是优势：接口形状本身就在阻止业务逻辑往 Dart 滑，因为 Dart 侧压根没有"我可以调一下 Rust 的业务函数"这个动作。

必须纠正的前提：Rinf v8 不用 protobuf。 它在 v8 的序列化是 serde + bincode，消息类型在 Rust 侧用 #[derive(Serialize, RustSignal)] 定义，Dart 类由 rinf gen 从 Rust struct 反向生成到 lib/src/bindings/。历史上（约 v5/v6，2024 年那批中文教程）它确实用 protobuf + .proto + 特殊注释 // [RINF:DART-SIGNAL]，那套写法已经过时了，别照着老教程做。

你要的"统一且高效的对象规约"没有丢，只是真相源从 .proto 变成了 Rust 类型。对"Rust 不动、Flutter 是外挂"这个目标来说这反而更优：schema 和实现是同一份文件，不会出现 proto 与 Rust 结构体漂移。如果你确实需要 protobuf 作为跨语言对外契约（比如未来还有 Web/其他客户端），有两条干净的接法：
  • prost + binary 字段：用 prost 在 Rust 侧编码成 Vec<u8>，塞进 Rinf 的 binary 字段，Dart 侧用 protobuf runtime 解。.proto 成为你真正的 schema，Rinf 只当传输层。
  • 单个 bytes 字段的 Rinf 消息：消息体只有 bytes payload = 1;，本质同上但少一层依赖。
两条都能同时拿到"protobuf 统一规约"和"Rinf 的高效传输"。我的建议是热路径（终端帧）用自定义紧凑二进制，控制面（连接目录、设置、认证）用 Rinf 的 serde 消息；只有当 protobuf 有外部消费者时才引入 prost。见 §5。

4.2 Rinf 给你的两个关键机制

机制语义对 rsHell 的意义
RustSignalBinary / DartSignalBinary 的 binary 字段 官方原文："designed to handle large binary data, potentially up to a few gigabytes… 当消息未标记为 binary signal 时该字段为空"；并且 "Sending a serialized message or binary data is a zero-copy operation from Rust to Dart" 这是终端帧的正确载体。帧不再走 serde，而是一块 Vec<u8>，Rust→Dart 方向无序列化开销。
rustSignalStream + StreamBuilder 的合并行为 官方原文："when using StreamBuilder, it may only process the latest message … they might skip some messages if multiple messages arrive within a single frame, typically around 16 milliseconds. To ensure that all messages from the stream are handled, you should consider using Stream.listen instead."；另有 latestRustSignal 取最近一帧 对帧来说，"丢弃中间帧"正是你要的语义——相当于免费的丢帧背压。而对字节流来说这是灾难——但我们的设计里字节流根本不过边界。于是这个"坑"在你的架构里恰好变成了特性。反过来，Dart→Rust 的按键信号必须用 Rust 侧的 get_dart_signal_receiver().recv().await 逐条消费，不能有"只取最新"的假设。
官方体积建议 "creating a signal larger than a few megabytes is not recommended" 给帧大小定了预算：单帧控制在 1 MB 以内是安全的（120×40 全量帧在几十 KB 量级，余量充足）。但这也意味着"一次性把 10 万行 scrollback 全量推给 Dart"是错误设计——历史滚动应该按需分页拉取，而不是预先全量镜像。

4.3 需要记账的风险（我不会替你美化）

  • Rinf 仓库 README 顶部挂着一条告示：维护者正在寻找接手人（"Looking for a New Maintainer… with full authority over the API design and build system going forward"）。这不是说它会死，但一个掌握你 iOS 构建链的框架处于"待交接"状态，是必须写进决策记录的长期风险。缓解手段：Rinf 的能力面很薄（dart:ffi + 消息编解码 + Cargokit 构建），必要时把它的 core 部分本地 vendor 或替换成手写 C ABI 的成本可控——这也是我下面建议"帧协议自己定"的原因：把依赖面收敛在传输层，别让它渗透进业务。
  • 没有 RPC：连接目录的增删改查、"列出会话"这类请求/响应语义，需要你自己用关联 ID建模（Request{id, payload} / Response{id, result}）。这是确定会写的样板代码，代价要算进去。
  • 逃生舱：Rinf 本身就建立在 dart:ffi 之上，所以同一个 hub crate 里再加几个 #[no_mangle] extern "C" 的裸 C ABI 函数是允许的，不会引入第二个框架。只把这招留给"必须同步、极低延迟"的极少数调用（例如 probe/健康检查），不要扩散。

五、帧协议：不要让 render frame 变成 DTO 洪水

5.1 先算清楚代价

rsHell 现有的 RenderFrame 是给 GTK 用的、语义正确的结构：

RenderFrame { generation, size, viewport_top, rows: Arc<[RenderRow]>, cursor, title, display_modes, alternate_screen, mouse_reporting }
RenderRow   { stable_row: i64, wrapped: bool, cells: Arc<[RenderCell]> }
RenderCell  { text: String, width: u8, foreground: Color, background: Color, attributes: CellAttributes, selected: bool }

它在 rshell-core 里不含任何 GTK 类型，这是好设计，必须保留。但如果把它原样序列化给 Dart，代价是：

方案120×40 全量帧60 Hz 下界问题
逐 cell 的 serde 结构体（RenderCell 直传）≈ 300 KB+ 且伴随 4,800 次 String 分配≈ 18 MB/s + 每秒 28.8 万次小对象分配Dart 侧 GC 压力会直接体现为掉帧；bincode 也救不了一次一对象的结构
紧凑二进制 + RustSignalBinary（本报告建议）≈ 57–77 KB（见下）≈ 3.5–4.6 MB/s（且只在脏时发）无分配洪水；配合脏行可以降到 KB 级

5.2 建议的 wire format（v0 = 正确性基线）

不要一上来就做增量。先用"每次全量快照"把正确性基线立起来，再按测量加脏行与样式 run——这是唯一能避免"性能优化掩盖语义 bug"的顺序。

// ── Rust 侧（rinf hub）
#[derive(Serialize, RustSignal)]      // 只带元数据，很小
struct RenderFrameMeta {
    session_epoch: u32,   // 会话代；重连/切窗口后拒绝旧帧
    generation:    u64,   // 帧序号，单调递增
    cols:          u16,
    rows:          u16,
    viewport_top:  i64,
    cursor_col:    i16,   // -1 = 无光标
    cursor_row:    i16,
    cursor_shape:  u8,
    flags:         u32,   // alternate_screen | mouse_reporting | cursor_visible | kitty_kb ...
    title:         String,
}

#[derive(Serialize, RustSignalBinary)]  // 二进制负载单独走，不过 serde
struct RenderFrameCells {
    generation: u64,          // 必须与 Meta 对上，防止错帧
    layout:     u8,           // 版本号，方便以后换布局
    cells:      Vec<u8>,       // rows*cols 个定长 cell，行主序
}

每个 cell 16 字节、行主序、不用任何 per-cell 结构体：

offset  size  field
0       4     codepoint: u32      // 已解决宽字符/组合字符的最终字形簇首码点，0 = 空
4       4     fg: u32             // 高 8 位 kind(0=default,1=ansi,2=rgb) | 低 24 位值
8       4     bg: u32             // 同上
12      1     attrs: u8           // bit0 bold, bit1 italic, bit2 underline, bit3 strike, bit4 reverse
13      1     width: u8           // 1 或 2（宽字符占位）
14      1     flags: u8           // bit0 selected, bit1 dim, bit2 wrapped, ...
15      1     reserved: u8        // 显式留白：以后加 OSC8 链接 id / 更多下划线样式不用改布局

120×40 = 4,800 cell × 16 B = 76.8 KB/帧；60 Hz 最坏全量 = 4.6 MB/s，远低于 Rinf 的"几 MB"建议线（因为我们每帧只发一块，不是发多个大消息）。而实践中软件光标闪烁、打字回显这种场景只涉及 1–3 行，配合 v1 的脏行机制就是 每帧 1.9–5.8 KB。

5.3 v1 才做增量：脏行 + 样式 run

  • 脏行差分：RenderFrameCells 的 rows 段改成"行号 + 该行 cell"，只发改动过的行。rsHell 的 alacritty_tracker.rs / alacritty_primary_rows.rs 已经在追踪滚动与行稳定性，脏行信息可以从那里低成本派生，不必重写。
  • 样式 run 压缩：同一行里连续同色同属性的 cell 合并成 run，是 v1 之后最省的一步。但要么等测量结果，要么就固定不做——不要同时改协议和加压缩。
  • 拒绝旧帧：session_epoch + generation 是硬要求。窗口重建、重连、切标签之后，管道里残留的旧帧必须被 Dart 侧丢弃，否则会出现"旧屏幕污染新会话"——这类 bug 在桌面 GTK 上或许只表现为闪一下，在移动端多窗口/分屏场景下会很难查。

5.4 Dart 侧的允许形态（示例）

Dart 只做"解码 + 画"。下面这段是允许的全部类型的逻辑——注意它没有任何状态机、没有 ANSI 解析、没有会话概念：

final sub = RenderFrameCells.rustSignalStream.listen((pack) {
  final cells = pack.binary;            // Uint8List，Rust→Dart 零拷贝
  final meta  = RenderFrameMeta.latestRustSignal?.message;
  if (meta == null || pack.message.generation != meta.generation) return; // 丢错帧
  _painter.applyFrame(meta, cells);     // 写进要 repaint 的缓冲
  _repaint?.call();
});

搭配 StreamBuilder（而非 listen）也可行，并且会额外获得"同帧内只处理最新"的天然丢帧；两种都能接受，取决于你想不想在 Dart 侧留一个缓冲。关键约束是帧里不许出现需要 Dart 记住的东西：如果某个字段要求 Dart 跨帧累计（例如"累计偏移量"），那说明协议设计错了。

六、iOS / iPadOS 逐项适配细节

6.1 渲染：Flutter 侧的唯一正确路径

因为你的约束是"渲染用 Flutter"，那就不要走 UiKitView/PlatformView + 原生 Metal 这条（那等于渲染仍用 Swift 写，违背前提）。纯 Flutter 路径是 CustomPainter + Canvas.drawParagraph，iOS 上由 Impeller(Metal) 承载。三个必须注意的点：

  • 行级 Paragraph，不是 cell 级 Widget。40 行 → 每帧最多构造 40 个 Paragraph（而不是 4,800 个 span 或 widget）。并且要按（行内容 + 样式签名）做 cache，只有脏行才重建 Paragraph。
  • 背景色块与文字分开画。先用 drawRect 画整行背景 run（同色连续段合并成一个 rect），再逐行 drawParagraph 画文字。这条顺序能省掉绝大多数 draw call。
  • 不要依赖"字体度量自由排版"。终端的每一列必须等宽对齐，所以要根据 Flutter 测出的 cell 尺寸反推行列数，再由 Rust 决定换行与内容——绝不能把整行交给普通 Text 自由排版后假设它和列网格一致。

如果（且仅如果）Gate B 测出 Impeller 路径达不到 16.7 ms 帧预算，再考虑字形图集 + drawRawAtlas 这条更重的路。不要提前做。

6.2 字体：iOS 上不能靠"系统装了什么"

rsHell 桌面版刚把默认字体改成 CaskaydiaCove NF Mono，那是 Nerd Font 派生字体。桌面版可以依赖宿主已安装，iOS 完全不行：

  • 必须打包字体进 bundle，并且许可证必须允许再发行（Cascadia Code 系为 OFL-1.1，可再发行；但你要自己核对最终选用的那份 Nerd Font patch 的授权）。
  • 必须显式声明 CJK / emoji / symbol 的 fallback 链，并验证宽字符占 2 列、组合字符（如 emoji ZWJ 序列）占 1 个字形簇——这直接决定 §5.2 里 width 字段的正确性。
  • UI 文字可以跟随系统无障碍字号缩放，终端字号与网格缩放必须独立控制，否则系统缩放会悄悄改变列宽，导致远端程序全屏 TUI 排版错乱。这是移动端特有的坑，桌面版没有。
  • 不能因为"某字体在 Windows/macOS 上已安装"就假设它在 iOS 上可用。

6.3 输入：三条独立通道，不能混

通道负责必须验证
物理键Esc / Tab / Ctrl / Alt / Meta / 方向键 / 功能键 / 组合键；交给 Rust 的 alacritty_key::encode 产出 CSI/CSI-u/kitty 序列按下/释放/重复三种事件；Cmd 组合在 iOS 上会被系统截获（如 Cmd+H 回主屏），产品上不能承诺"接管全部系统快捷键"——为无法截获的组合提供命令面板或屏幕功能键
文本/IME中文拼音、日文假名等 composition 过程只在本地呈现，提交后才作为 CommittedText 发给 Rust不重复字符、不漏 Backspace、未提交的 preedit 绝不外发；候选框跟随光标
辅助键条软键盘没有 Ctrl/Esc/方向键，必须有屏幕按键条且支持修饰键锁定与硬件键盘同时存在时不重复触发；不因检测到触摸屏就禁用键鼠

rsHell 现有契约里有一条必须原样保留：普通 Ctrl+C 只发且仅发一次 ETX(0x03)，复制走 Ctrl+Shift+C；仍存活的 TUI 不该因为收到 Ctrl+C 就被强制退出备用屏幕。移动端把这个契约做成三个不同的命令（安全中断 / 复制 / 显示恢复），不要简化成"Ctrl+C 就是复制"，也不要"一中断就无条件 reset"。

6.4 触控与终端模式冲突（移动端独有）

远端 Vim / tmux 打开 mouse reporting 之后，手指拖动到底是"滚动本地历史""选字"还是"给远端发鼠标事件"？桌面靠修饰键区分，触控端没有等价物。必须给出显式的模式切换（本地选择模式 / 远端交互模式），并且在 UI 上可见。需要覆盖的终端模式至少：普通 shell、备用屏幕全屏 TUI、application cursor、mouse reporting、bracketed paste、kitty keyboard、选择/搜索模式、连接失败恢复态。

6.5 生命周期：后台必断，不要假装不断

  • iOS 在进入后台后很快挂起进程，TCP 连接虽然在内核里可能还没被回收，但应用无法处理数据。不要用假音频/假 VoIP background mode 来续命——那是审核红线，而且耗电。
  • 正确做法：进后台时保存工作区元数据、停止绘制、取消外设交互；回前台时探测并区分"仍连通 / 正在重连 / 会话已结束"三种真实状态。
  • "恢复远端工作"应设计为重连后回到服务器端持久会话（tmux/screen），而不是"恢复原来的 TCP 连接"。并且绝不自动重放用户最后一条命令——那会重复执行有副作用的操作。
  • Mosh 之类的协议如果想上，单独立项，不是 russh 的一个开关。

6.6 内存：桌面契约在手机上会触发 jetsam

rsHell 的终端引擎门禁契约是 100 MiB × 5（脚本 scripts/qa/terminal-engine-gate.ps1，120×40、1000 行滚动缓冲 p95、SHA-256 比对）。这在桌面是加分项，在 iPhone 上最多可到 500 MiB 的终端缓冲——iOS 会因为内存压力直接杀掉应用（jetsam），而且用户看到的不是"卡"而是"闪退"。

因此 iOS 必须另有 terminal profile： 把 scrolling_history 从行数/字节上限两个维度重新设限（例如按设备内存分级：手机 2–5k 行、iPad 10k 行），并且 scrollback 必须计入"多会话总预算"而不是每会话独立预算。现有的 GO 门禁可以作为回归基线保留在桌面，但不能作为 iOS 的验收标准；iOS 需要自己的一组内存上界测试。

6.7 剪贴板、链接与图像协议

  • 剪贴板：走 UIPasteboard。特别要处理 OSC 52——远端程序请求写系统剪贴板时，必须经过用户确认或有明确策略，不能无条件执行。
  • OSC 8 超链接：桌面版已支持渲染，Flutter 侧要重新实现（命中测试 + 打开前的 scheme 白名单校验）。
  • 图像协议（Sixel / iTerm2 / Kitty）：桌面版 changelog 显示已支持，但这套东西在 GTK 侧是自实现的。首版建议明确砍掉，理由：解码、缓存、与滚动缓冲的交互、脏区重绘都要在 Flutter 侧重做一遍，而它对"SSH 终端能用"不是必需。砍掉要写进不承诺清单，别让用户以为"Flutter 版会有"。
  • 终端输出视为不可信数据：超长 escape 序列、异常 Unicode、内存增长、日志内容都要设限；不要把远端文本当本地命令执行。

七、必须改动清单（可直接开工）

7.1 Rust 侧

#改动具体做法 / 依据

7TERM 的处理路径换掉不要走 alacritty 的 setup_env() / terminfo 探测（iOS 上没有 terminfo 数据库）；TERM 应当作为 SSH pty-req 的参数字符串由应用显式指定。
8可选：缩小 alacritty 依赖面给 tty 模块加 pty feature（一行 cfg）。不是必须的，只做体积优化。不要为此维护大规模 fork。

7.2 Flutter 侧（只允许做这五件事）

  1. 会话列表 / 连接编辑 / 设置的视图（数据全部来自 Rust 信号）。
  2. TerminalSurface：CustomPainter 绘制 + 命中测试 + 选择手柄 + 语义（无障碍）。
  3. InputAdapter：物理键 / IME / 触控 / 指针 / 粘贴，产出 DartSignal；不含任何协议编码逻辑。
  4. 平台服务插件：Keychain（经 Rust 的 vault 端口）、UIPasteboard、文件导入、生命周期。
  5. 按"窗口可用空间 × 输入设备 × 终端模式"做布局适配（不是 OS 分支）。

判定标准很简单：如果某段 Dart 代码需要知道"当前是备用屏幕"或"CSIU 模式开着"，那它放错地方了。

Flutter 端到端		 帧协议、绘制、字体度量、输入法在真实负载下的正确性与性能 待做。复用 rsHell 已有的字节语料与滚动缓冲契约做参考输出；覆盖 bash/zsh 提示符、全屏 TUI、主/备用屏切换、UTF-8 分块、搜索选择、中断恢复。新增测量项：FFI 时间、raster 帧时间、帧分配量、Rust→Dart 二进制传输开销、输入到本地呈现延迟、能耗。目标 16.7 ms，但不许在没有测量前宣称达到。
C
iOS 输入与生命周期		 移动端特有的一整类问题 待做。软键盘（拼音/日文/连续删除）、硬件键盘（Ctrl/Alt/Meta/Esc/重复/释放）、触控选择 vs 远端鼠标报告、键盘升降与旋转与分屏 resize 后会话不重建、锁屏/后台/网络切换/终止恢复、内存上界（大输出 + 多会话 + 频繁重连）。
D
审核与分发		 能否上架 待做。SSH 客户端上架没有障碍（Blink/Termius 先例）；只要不碰本地 shell 与代码执行，2.5.2 就不会咬你。需要的 entitlement（Keychain 访问组等）与真实发行构建签名要单独验。

什么不算通过：Flutter 页面能启动、Rust 的 greet 返回、字体量出来一个格子大小、本地 cargo build 成功——都不算。必须走完"真实 SSH 认证 + 正确终端状态 + 可靠输入与取消 + 真机证据"。

九、与你朋友那份报告的差异

议题那份报告本报告
alacritty 能否上 iOS给到"建议先尝试直接构建所需终端路径；若被未使用的 PTY/信号模块阻塞，再做最小 feature 分离或维护小型补丁"——结论悬置已实测闭环：编译 ✅、链接 ✅（_openpty/_fork 从 libSystem 解析）、VT 语义 ✅、本地 PTY ❌。因此"是否需要补丁"的答案是不需要。
终端状态机的归属把 xterm.dart 列为"主要备选"，并描述了"Rust 的 SSH 输出原始字节 → 流式 UTF-8 解码 → 喂给 Dart terminal，Dart 的键盘编码写回 SSH"这条路径明确反对。那等于把终端状态搬到 Dart，与"业务留在 Rust、不改"直接冲突，并且会产生两份状态权威。备选方案应当是把 Rust 的 SSH 换掉（dartssh2），而不是把终端换掉——但那同样违背前提。
桥的选择flutter_rust_bridge（RPC 风格，有类型化异步调用）按你的指定用 Rinf。顺带指出：Rinf 的接口形状（单向信号、没有 RPC）比 FRB 更能阻止业务逻辑滑向 Dart，这对你的约束是加分；代价是 CRUD 需要自己用关联 ID 建模。
消息规约—（未涉及）纠正一个前提：Rinf v8 是 serde + bincode + Rust derive，不是 protobuf。若要用 protobuf 作为对外统一规约，走 prost → binary 字段 这条接法。
iOS 内存提到 100 MiB×5 是"已有工程资产"、不是基准测试（判断正确）进一步给出行动结论：该契约在 iOS 上会导致 jetsam 杀进程，必须另设平台分级的 scrollback 上界。
硬件密钥 / 智能卡 / 鸿蒙占了相当篇幅（FIDO2、PIV、OTG、HUKS…）本次不展开。你的诉求是"Flutter 前端 + iOS + alacritty 能不能跑"，那部分属于另一条产品线，建议单独决策。仅提示一条边界：SSH 客户端主体不依赖它们，别让它们拖慢主线。

十、明确不承诺的东西

  • iOS 上的本地 shell / 本地 PTY：不可能。不要在任何界面或文案里暗示它存在。
  • 移动端后台常驻连接：iOS 会挂起；"恢复工作"= 重连 + 服务器端持久会话，不是保持 TCP。
  • Sixel / iTerm2 / Kitty 图像协议：首版砍掉（桌面已有，Flutter 侧需重做）。
  • 与桌面完全一致的快捷键：Cmd 组合在 iOS 上属系统保留，必须提供替代路径（命令面板 / 屏幕功能键）。
  • 桌面级的 scrollback 容量：见 §6.6。
  • "换成 Flutter 就消除了字体与终端兼容问题"：恰恰相反，iOS 上字体必须自带并显式声明 fallback。
  • 按帧全量镜像 scrollback 给 Dart：违反 Rinf 的单消息体积建议，也不符合 §5.3 的按需分页设计。
