〇、结论先行：三个改变计划的发现

上一份可行性报告的结论是「可以做，Rust 侧比想象中干净」。这次为了定里程碑，我把仓库 clone 下来读到了传输层，结论要往前推两步——两份报告之间，MVP 的成本量级变了。

发现 1：rsHell 不是「本地终端 + 可选 SSH」，它本来就是一个 SSH 客户端。 crates/rshell-session/src/transport/ 下有四个传输实现，其中 native_ssh.rs 是纯 russh + tokio::net::TcpStream 的托管 SSH： client::connect_stream() → AuthPlan::Password 认证 → channel_open_session() → request_pty(term, cols, rows, px_w, px_h) → request_shell()。 PTY 开在远端，本地一个 fork 都不需要。你要的「写死地址和密码验证 SSH」，不是要从零搭的东西，而是仓库里已经写好的东西——只是从来没人把它编译到 iOS 上跑过。
发现 2：Flutter 与 Rust 之间的边界，仓库里已经存在，而且已经是可序列化的。 rshell-core 有一个完整的 protocol 模块：UiCommand / AppEvent（应用级：连接目录、设置、导入、分屏、标签）与 SessionUiCommand / SessionUiEvent（会话级：输入、缩放、滚动、搜索、选择、交互应答）。 更关键的是，RenderFrame / RenderCell / TerminalInput / InteractionRequest 等全部类型都已经 #[derive(Serialize, Deserialize)]。 GTK 层（rshell-ui，22812 行）就是靠这套类型跟内核说话的。换掉 GTK，边界不用重新设计。
发现 3：M0 已经端到端跑通了，不是推测。 我在本机起了一个最小 russh 服务端，用 rsHell 自己的 NativeSshTransport 走了完整路径，拿到了： request_pty 的实际参数（xterm-256color / 80×24）、远端 shell 的开场字节、写路径回显、主机密钥 TOFU 落盘。 同时 iOS 三个目标（host / device / sim）全部构建通过，链接产物里没有任何 fork / openpty / posix_spawn。见下一节。

这三条合起来的效果是：MVP 的第一步从「搭一套 FFI 框架 + 重写终端」降级成「把一个已有 crate 编到 iOS 上，喂它一个写死的 ConnectionProfile」。真正的工作量仍然在后面（渲染与输入），但它现在可以一块一块地验证，而不是压在一次大集成上。

1.3 一个必须写进设计的负面发现

M0 的读循环必须有截止时间，不能等 EOF。 我第一次跑环回测试时它永久挂住了。原因不是 bug：真实远端 shell 既不会 Eof，也不会给 ExitStatus——它会一直等你的下一条输入。只有 exec 模式（ConnectionProfile::remote_command 非空）才会有退出码。
「连上 → 读 → 等 Eof → 打印结果」这个最自然的写法，在真机上就是一个永远转不完的循环。M0 的读循环必须带总时长上限（我们用 10 s），M2 之后则由 Flutter 侧的会话生命周期来控制。

1.4 顺带确认的两件 M1 前置条件

  • serde 必须开 rc feature。RenderFrame.rows 与 RenderRow.cells 的类型是 Arc<[..]>。serde 默认不实现 Arc 的序列化，不开 rc 就会在 serde_json::to_string(&frame) / bincode 编码处报 trait 不满足。已在新 crate 里打开。
  • RenderFrame 可以跨线程搬运。frame_is_send() 把帧从引擎线程移到另一个线程再读回，编译通过。rinf 在独立线程发信号，这条必须先立住。

二、关键里程碑 M0–M4

每个里程碑只增加一类未知量，前一个的绿是后一个的前提。这是刻意的：M0 挂了你只怀疑 SSH，M1 挂了你只怀疑渲染，不会被混在一起。

M0SSH 直连 —— 写死地址和密码，先在真机上跑通代码已就绪

做什么。把 rshell-session 编成 iOS 静态库，Rust 侧写死一个 ConnectionProfile{ NativeSsh, Password }，用 AuthPlan::from_secret() 直接吃明文密码（不读 vault），连上一台真实服务器，把字节打出来。没有渲染、没有输入、没有 UI。

拆成两步，把风险再切一刀：

  • M0a（macOS，不需要 Xcode）—— 本报告已跑通。验证 SSH 逻辑、认证、TOFU、请求序列。
  • M0b（真机）—— 同一个 Rust 函数，唯一剩下的未知量就是 iOS 沙箱。

宿主用什么。建议一个只有「一个输入框 + 一个按钮 + 一块文本」的 Flutter 页面，用 dart:ffi 直接调 C ABI rshell_m0_smoke()。这一步先不接 rinf：M0 要回答的是「SSH 在 iOS 沙箱里通不通」，把 rinf 的构建集成混进来会污染信号。Rust 产物在两种宿主下是同一个 .a，不返工；rinf 留到 M1 与结构化信号一起接。

验收（全部满足才算绿）：
  • 真机上 rshell_m0_smoke() 返回 ok=true，transcript 里能看到远端 shell 的提示符或欢迎信息。
  • 失败时返回明确分类的 SessionFailure（Network / Authentication / HostKey / SshChannel），而不是一句笼统的错。
  • 写路径回显成功（transport.write() 的字节被远端收到）。
  • known_hosts 在 App 沙箱内落盘，第二次连接不再触发主机密钥交互。
M1一帧终端画面 —— 接入 rinf，画出只读网格

做什么。把 M0 拿到的字节喂进 DefaultTerminalEngine::advance()，调 render(viewport, selection) 拿到 RenderFrame，经 rinf 信号过边界，Flutter 侧用 CustomPainter 画出来。仍然只读，不处理输入。

为什么先只读。渲染是这条路上唯一有真实性能风险的地方，而输入是唯一有真实平台风险的地方。分开测，出问题立刻知道该看哪边。

度量权威的划分（重要）。TerminalSize 里的 cols/rows/pixel_width/pixel_height/dpi 必须由 Flutter 测量后回传：字体度量只有一个权威，就是实际画字的那一方（Flutter）。Rust 侧的 alacritty 只负责网格状态，不负责判断单元格有几百像素宽。仓里 alacritty_adapter.rs 已经是「尺寸由外部传入」的设计，不需要改。

验收：
  • iPhone / iPad 上出现完整着色的终端画面，ls --color=always 与 git log --color 颜色正确。
  • CJK 按 2 列宽渲染、emoji 与零宽字符不错位（render.rs 里已有 WIDE_CHAR / ZEROWIDTH 处理，验证它被正确消费）。
  • 旋转或改窗口尺寸 → SessionUiCommand::Resize → 远端 WindowChange → 远端 stty size 的输出随之变化。
  • 连续刷新（top / htop）下掉帧可接受，且 rinf 的「只保留最新信号」语义让丢帧表现为晚一帧而不是花屏。
M2输入闭环 —— 软键盘、IME、Ctrl/Esc

做什么。Flutter 的 TextInputClient / 硬件键盘事件 → TerminalInput::{CommittedText, Key{code, modifiers}} → Rust 的 encode_input()（alacritty 的键编码，含 Kitty / CSI-u 协商）→ transport.write()。

边界上的一个硬约束：secret 类型不能序列化。SessionUiCommand::Paste(SecretString) 与 InteractionResponse::Secret(SecretString) 刻意没有 serde 派生。所以 Dart 侧只能传明文，Rust 侧在接收处自己包成 SecretString。这是设计意图，不是缺陷——但意味着协议层要手写一层「明文 → 秘密」的转换，不能直接 derive 完事。

验收：
  • iPhone 上能跑 vim：进入、编辑、:wq 保存，全过程正常。
  • Ctrl+C 精确发出一个 ETX（0x03），不管远端有没有协商 Kitty 键盘。
  • 中文 IME 的 preedit 绝不外发；只有 committed text 过边界。
  • Ctrl/Esc/Tab/方向键在软键盘上可达（快捷键行或 inputAccessoryView）。
M3连接管理与凭证 —— 把写死的东西换成真的

做什么。用 Flutter 原生表单做连接编辑，密码/私钥口令存进 iOS Keychain。Rust 侧的接口已经现成：AuthPlan::from_profile(&profile, &vault) + rshell-storage 的 CredentialVault，只要在 iOS 上走通 apple-native-keyring-store 的 protected 后端（这正是 M0 唯一那个必修补丁打开的 feature）。

顺带能白拿的：UiCommand::ApplyCatalog / AppEvent::CatalogChanged 与 ImportSourceKind 系列意味着连接目录、分组、导入（含 SSH config / 其他客户端迁移）的逻辑都在 Rust 里。Flutter 只需要做表单和列表，不需要在 Dart 里重写一份业务模型。

验收：
  • 新增 / 编辑 / 删除连接，密码进 Keychain，杀进程重启后仍在。
  • 首次连接的主机密钥确认走真实 UI（InteractionRequest::HostKey → HostKeyPrompt{sha256, changed}），不再是 TOFU 自动接受。
  • 主机密钥变更时给出 changed=true 的显式警告，不静默接受。
M4产品化与合规
  • 多标签 / 分屏。PaneTree / SplitAxis / WorkspaceState 已在 rshell-core 里，UiCommand::{Split, ClosePane, CloseTab} 也已在协议里。Flutter 侧做手势与布局。
  • 滚动回看的分级上界。桌面那条 scrollback_lines 契约（上限 1_000_000 行）在手机上会触发 jetsam 直接杀进程。必须另设平台分级上界，不能沿用桌面默认值。
  • 生命周期。App 进后台后 SSH 连接怎么处理（保活 / 断连 / 重连），SessionUiCommand::Reconnect 与 SessionState 状态机已在 Rust 侧。
  • 分发合规。App Review 2.5.2 对「可执行任意代码 / 远程 shell」类应用有限制，定位与描述需要提前想清楚。

三、M0 交接单

可运行代码已经放在 rshell-ios-m0/。

文件作用
setup.sh幂等准备：把 rsHell clone 到 ../rsHell 的固定 commit、打上 iOS keyring 补丁、装 iOS 编译目标
src/lib.rsM0 全部逻辑：smoke() / blocking_smoke() / C ABI rshell_m0_smoke()；另附 engine_smoke()、frame_is_send() 作为 M1 前置验证

3.1 唯一必修的依赖补丁

rshell-storage 的 Cargo.toml 需要追加（setup.sh 会自动做）：

crates/rshell-storage/Cargo.toml 追加
[target.'cfg(target_os = "ios")'.dependencies]
apple-native-keyring-store = { version = "1.0.1", features = ["protected"] }

原因是 keyring 4.1.5 的 v1 feature 只启用 apple-native-keyring-store/keychain，而 iOS 上根本没有 legacy keychain，只有 protected data store，不补这个 feature 会直接编译失败：error: The `protected` feature is required on iOS。这是整个 Rust 后端在 iOS 上唯一一处硬阻塞。

3.2 M0b 的真机步骤

  1. ./setup.sh → cargo build --release --lib --target aarch64-apple-ios
  2. 建一个 Flutter App 工程，把 librshell_m0.a 作为静态库链进去（或写一个最小 Flutter plugin，ios/ 下挂 vendored_libraries + 一个 bridging header 声明 rshell_m0_smoke）。
  3. 一屏页面：host / port / user / password 四个输入框 + 一个按钮 + 一块可滚动文本。dart:ffi 调 rshell_m0_smoke()，把返回的 JSON 里的 text 显示出来。这一步是暂时的，M1 会被 rinf 取代。
  4. 真机跑。看 transcript 里的提示符。
三个真机陷阱，按踩坑概率排序。
  1. 别用模拟器验收。模拟器跑在 macOS 用户态，fork / openpty 全都在。拿它测「本地 PTY 在 iOS 上不工作」会得出错误结论（会「能跑」），反过来也会掩盖别的沙箱问题。M0 必须真机。
  2. 局域网目标机会被本地网络隐私拦住。iOS 14+ 起，连局域网地址需要 NSLocalNetworkUsageDescription，首次连接会弹权限框；未授权时 connect() 表现为静默超时，不是报错——这会让人误判成 SSH 有问题。公网 VPS 没有这个问题。另外 macOS 目标机默认关闭「远程登录」，要先打开。
  3. 读循环必须有截止时间（见 1.3）。等 EOF 就是永久挂住。

3.3 已完成的环境改动

为了做实测，本机加了两条命令（幂等、可随时撤销）：

rustup target add aarch64-apple-ios aarch64-apple-ios-sim

四、复用 / 重写清单

这一节直接决定工作量。按 find src -name '*.rs' | xargs cat | wc -l 实测：

Crate行数iOS 上的处置
rshell-core4,240全量保留。领域模型、连接目录、终端设置、RenderFrame 类型、protocol 模块——全部与平台无关。
rshell-session7,036保留，去掉 transport/local*、transport/pty、transport/system_ssh（iOS 死代码，实测已被链接器裁掉）。native_ssh、alacritty_*、engine、manager、actor 全保留。

这个比例值得直视。 要重写的 Flutter 层（约 2.7 万行）是它要对话的 Rust 内核（1.1 万行）的 2.4 倍。 「Rust 不动」这个目标本身达成了——但达成它的代价是：绝大部分新代码是渲染与交互。这也是为什么 M1 的渲染性能是整个计划里唯一需要提前验证的技术风险。

4.1 四个传输在 iOS 上的可达性

传输iOS原因
native_ssh（russh）可用纯 TCP + russh，PTY 开在远端。零 fork。已实测链接产物不含任何 PTY 符号。
system_ssh不可用靠 build_system_ssh_argv 启动系统 ssh 可执行文件。iOS 沙箱不允许 spawn 进程。
local（portable-pty）不可用需要 fork + openpty。iOS unistd.h 里根本没有 fork 声明，沙箱也禁止。
pty不可用同上，是 local 的底层。

好消息是这三个不可用的传输都在 rshell-session 内部，不需要从产品里「删功能」：iOS 侧的 Flutter 只要不暴露对应的入口即可，Rust 侧零改动。

五、决策台账

5.1 我已经替你定的（不反对就照此执行）

决定理由
M0 拆成 M0a（macOS 命令行）+ M0b（真机）M0a 不需要 Xcode、不需要真机、不需要外部服务器（环回测试），已经跑通。M0b 于是只剩「沙箱」一个未知量。
M0b 用 Flutter + dart:ffi 直调 C ABI，先不接 rinfrinf 的构建集成是一个独立未知量，混进 M0 会让失败无法归因。Rust 产物两种宿主通用，不返工。
主机密钥策略：M0 用 TOFU（接受并落盘），M3 换成真实 UI 确认M0 的前提是「不接 UI」，走完整交互确认会自相矛盾。TOFU 落盘 + 第二次不再询问，已经足够验证交互链路是活的。这是明确的技术债，必须在 M3 还清。
复用 rshell-core::protocol 的 UiCommand/AppEvent，不在 Dart 里重建业务模型连接目录、分组、设置、导入、分屏状态机都在 Rust 里且已可序列化。在 Dart 重写一份等于违反「业务用 Rust 跑」的前提。
帧的形态：传结构化 RenderFrame，Flutter 侧画见 5.2 第 3 条待确认项——我倾向这个，但它影响 M1 是否返工，所以列为待定而不是已定。
不要在 release profile 里设 panic = "abort"rsHell 的 actor 靠 catch_unwind 把 panic 转成 SessionEvent::Crashed（仓库里有 actor_panic_gtk_survival_macos 测试守着）。abort 会直接毁掉这条韧性设计。

六、风险登记册

风险等级现状与应对
Flutter 侧逐 cell TextPainter 的性能高整条路线唯一需要提前验证的技术风险。120×40 = 4,800 cell/帧，60 fps 下是 28.8 万 cell/s。必须做「行内相同样式合并成 run + 字形缓存」，不能一个 cell 一个 TextPainter。M1 就要压测到目标帧率，不能留到 M4。
rinf 信号会丢弃中间消息中对终端帧这是免费的丢帧背压（表现为晚一帧），对字节流是灾难。所以设计上字节流根本不过边界——Rust 是唯一状态权威。SessionClient.frames 本来就是 watch::Receiver（只保留最新），语义天然对齐。
iOS 内存上限触发 jetsam中桌面 scrollback_lines 上限 1_000_000 行在手机上会被系统直接杀进程。M4 必须设平台分级上界。
App Review 2.5.2中远程 shell / 可执行任意代码类应用有额外要求。M4 前要确定定位与描述策略。
iOS 后台生命周期中进后台后 SSH 连接会被挂起。重连 / 保活策略要做成显式的产品行为，不能靠「不断开」蒙混。SessionUiCommand::Reconnect 已在协议里。
软键盘缺少 Ctrl / Esc中iOS 软键盘没有这些键，必须自建快捷键行。Cmd 组合会被系统截获，能用的默认修饰键只有 Ctrl / Alt（还有长按）。
russh / ring 的 iOS 编译已消除device / sim 双目标实测通过。
alacritty_terminal 在 iOS 上编译已消除零改动通过，且 tty 模块的死代码被链接器裁掉。
Rust 后端整体在 iOS 上编译已消除唯一阻塞是 keyring 的 protected feature，已定位并给出补丁。
SSH 认证 / PTY / 请求序列的正确性已消除环回端到端跑通，参数、字节流、写路径、TOFU 全部验证。
